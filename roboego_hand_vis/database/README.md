# 数据登记与下载状态数据库

使用 PostgreSQL 管理共享目录中的数据。三张表为 `l1data`、`l2data`、`l3data`；
Python 接口也接受 `L1data` 等大小写写法。每张表包含以下四个基础字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | 各表独立自增，允许跳号 |
| `ks3_path` | `TEXT NOT NULL UNIQUE` | KS3 完整路径，表内唯一 |
| `download_status` | `TEXT NOT NULL DEFAULT 'pending'` | `pending`、`processing`、`completed`、`failed`、`block` |
| `local_path` | `TEXT NULL` | 相对于共享目录根路径的路径，未下载时为 NULL |

L1 另外包含 `config/l1_fields.yaml` 中的 12 个阶段状态字段，共 16 列；
L2、L3 目前各有 4 列。阶段状态字段均为 `TEXT NOT NULL DEFAULT 'pending'`，
所有下载和阶段状态字段统一允许 `pending`、`processing`、`completed`、`failed`、`block`。`block` 表示流程被阻断，是否使用由具体流程决定；`threshold_gate` 仅是门禁标记，不会自动设置状态。`completed` 表示阶段执行完成，
不自动代表质量门禁通过；YAML 的 `threshold_gate` 仅作为可能的门禁标记。
当前配置不会自动运行阶段或执行依赖检查。

独立的[基础质检数据库入口](../raw_headband_integrity/README.md)约定：
`raw_headband_integrity_status=completed` 必须表示门禁通过；门禁不通过写入 `block`，执行异常写入 `failed`。
该入口只更新此阶段状态，原来的单 session 命令不会回写数据库。

已有数据库统一五种状态时，先填写数据库连接配置，再执行
`migrations/003_unify_status_values.sql`，执行方式见下文“已有数据库统一状态”。
该迁移覆盖三张表的下载状态及 L1 的全部阶段状态，可以重复执行；不会更改已有记录。

下载状态同样允许五种取值，并要求下载 `completed` 记录有非空路径。
数据库只保存元数据，不保存视频等文件，也不负责实际访问 KS3。
不同层级的 ID 没有隐含关联，定位记录需要同时使用表名和 ID。

## 代码结构

```text
database/
├── model.py        # L1Data / L2Data / L3Data ORM 模型、TaskStatus 枚举
├── database.py     # 连接池、Session、事务提交与回滚、显式建表
├── data_service.py # 数据登记、查询、并发领取和状态流转
├── ingest.py       # 批量入库命令，识别新增与已存在记录
├── validators.py   # KS3 路径和共享相对路径校验
├── config/         # L1 阶段字段、依赖和可能的门禁标记
├── migrations/     # 已有表的显式 SQL 迁移
├── __init__.py     # 导出 Database、DataService、模型和状态枚举
└── __main__.py     # 命令行建表入口
```

`data_service.py` 使用 `database.py` 管理事务，并调用模型和路径校验。
`database.py` 依赖模型完成建表；模型与工具函数不依赖 service 或连接管理层。
三个模型各自显式定义四个字段，不使用共用字段基类。后续分别修改 `L1Data`、
`L2Data`、`L3Data` 类中的字段，并通过数据库迁移更新已有表。
外部仍通过 `from roboego_hand_vis.database import DataService, get_database_url` 使用接口。

需要直接使用 ORM 时，可显式管理 Session：

```python
import os
from sqlalchemy import select
from roboego_hand_vis.database import Database, get_database_url, L1Data, TaskStatus

database = Database.from_url(get_database_url())
try:
    with database.with_session() as session:
        records = session.scalars(
            select(L1Data).where(L1Data.download_status == TaskStatus.PENDING.value).limit(10)
        ).all()
        for record in records:
            print(record.id, record.ks3_path)
finally:
    database.close()
```

`with_session()` 每次创建独立 Session，正常退出时提交，异常时回滚，最终关闭。
不要跨线程共享 Session。模型中的 `download_status` 仍是 TEXT 字段，
使用 `TaskStatus.PENDING.value` 等小写值；状态限制由数据库 CHECK 约束保证。
普通 ORM 查询不代表领取任务，下载前仍须调用 `DataService.claim()`。

## 初始化步骤（系统 PostgreSQL）

统一使用系统安装的 PostgreSQL。当前服务器使用 PostgreSQL 14，地址为
`127.0.0.1:5432`，数据库名和数据库用户名均为 `roboego`。
以下命令在 Bash 终端执行。

### 1. 进入项目并安装依赖

在项目根目录执行：

```bash
conda activate ego
python -m pip install 'SQLAlchemy>=2.0,<3' 'psycopg[binary]>=3.2,<4'
```

依赖安装一次即可。仅操作数据库不需要安装视觉模型依赖。

### 2. 确认系统数据库正在运行

```bash
pg_lsclusters
pg_isready -h 127.0.0.1 -p 5432
```

预期 `14 main 5432 online`，且连接检查显示 `accepting connections`。
如果当前服务器的 `14 main` 集群未启动，执行：

```bash
sudo pg_ctlcluster 14 main start
```

其他服务器使用 `pg_lsclusters` 显示的版本、集群名和端口。
`pg_isready` 只检查服务是否接受连接；账号和密码在后续步骤验证。

### 3. 首次创建数据库用户和数据库

先检查是否已经存在：

```bash
(cd /tmp && sudo -u postgres psql -X -d postgres -c "SELECT rolname FROM pg_roles WHERE rolname = 'roboego';")
(cd /tmp && sudo -u postgres psql -X -d postgres -c "SELECT datname, pg_get_userbyid(datdba) AS owner FROM pg_database WHERE datname = 'roboego';")
```

只执行缺失对象对应的创建命令；如果之前已创建成功，直接跳到第 4 步。

```bash
# 仅当用户 roboego 不存在时执行。
(cd /tmp && sudo -u postgres createuser --pwprompt roboego)

# 仅当数据库 roboego 不存在时执行。
(cd /tmp && sudo -u postgres createdb --owner=roboego roboego)
```

密码提示的区别：

- `[sudo] password for <当前用户名>:`：系统登录密码。
- `Enter password for new role:`：为数据库用户 `roboego` 设置新密码。
- `Enter it again:`：再次输入相同的新密码。

输入密码时不显示字符。命令在 `/tmp` 下执行，可避免 postgres 系统用户无法
进入项目目录的提示。上述命令只创建项目专用用户和数据库。

### 4. 配置数据库连接（只需一次）

编辑 `roboego_hand_vis/database/config/database.yaml`，填写第 3 步设置的数据库密码：

```yaml
postgresql:
  host: 127.0.0.1
  port: 5432
  database: roboego
  username: roboego
  password: "你的数据库密码"
```

所有数据库命令都会自动读取此文件，刷新终端后无需重新 `export DATABASE_URL`。密码直接填写，不需要手动 URL 编码。
按当前私有仓库的使用要求，该配置文件保存在仓库中。

若当前进程设置了 `DATABASE_URL`，则优先使用环境变量；未设置时才读取 YAML。
连接其他服务器时，修改主机、端口、用户名和数据库名即可。

### 5. 初始化三张业务表

```bash
python -m roboego_hand_vis.database init
```

成功时输出：

```text
Initialized l1data, l2data, l3data
```

该命令读取环境变量或上述 YAML 连接配置，调用 `database.py` 中的 `Database.initialize()`，
根据 `model.py` 创建三张表。它不会创建 PostgreSQL 服务、数据库用户或数据库本身。
`data_service.py` 负责后续的数据登记和下载任务管理。

`init` 可重复执行，只创建缺失的表，不清空已有数据，也不修改已有表的字段。
后续新增字段应使用显式 SQL 迁移或 Alembic。

### 已有四字段 L1 表的升级

如果之前已经执行过 `init`，仅修改模型后再次运行 `init` 不会新增列。
在项目根目录、配置好数据库连接 后，执行以下迁移，再使用数据服务：

```bash
python - <<'PYMIGRATE'
import os
from pathlib import Path
from sqlalchemy import text
from roboego_hand_vis.database import Database, get_database_url

database = Database.from_url(get_database_url())
try:
    sql = Path("roboego_hand_vis/database/migrations/001_add_l1_stage_status.sql").read_text()
    with database.with_session() as session:
        session.execute(text(sql))
    print("Added L1 stage status columns")
finally:
    database.close()
PYMIGRATE
```

该迁移仅给 `l1data` 新增 12 列，保留原记录和下载状态；新增列默认是 `pending`。
可重复执行，已存在的列会跳过。新建数据库直接运行 `init` 即包含全部 16 列。

### 已有数据库统一状态

所有下载和阶段状态字段统一支持五种状态。已有数据库需执行 `003_unify_status_values.sql` 更新所有状态 CHECK 约束，不必单独执行 `002`。已安装数据库依赖后，先按上面第 4 步填写连接配置，再在项目根目录执行：

```bash
python - <<'PY'
import os
from pathlib import Path
from sqlalchemy import create_engine, text

from roboego_hand_vis.database import get_database_url
url = get_database_url()
engine = create_engine(url)
try:
    sql = Path("roboego_hand_vis/database/migrations/003_unify_status_values.sql").read_text()
    with engine.begin() as conn:
        conn.execute(text(sql))
finally:
    engine.dispose()
print("所有状态字段已统一为五种取值，允许 block")
PY
```

迁移可以重复执行，不改已有记录。历史上因门禁不通过而写入 `failed` 的记录不会自动改为 `block`；仅凭旧状态无法区分门禁不通过和执行异常。新数据库初始化直接包含该约束。

### 常见报错

| 报错 | 处理方式 |
| --- | --- |
| 提示填写数据库连接配置 | 按第 4 步填写 `config/database.yaml` |
| `password authentication failed` | 检查数据库用户名和密码；设置环境变量不会修改数据库密码 |
| `database "roboego" does not exist` | 完成第 3 步的建库命令 |
| `role "roboego" already exists` | 用户已存在，跳过建用户步骤，使用已有密码 |
| `database "roboego" already exists` | 数据库已存在，跳过建库步骤 |
| `connection refused` | 检查服务状态、主机地址和端口 |
| `permission denied for schema public` | 请管理员检查目标数据库的所有者和 schema 权限；新库应以 `roboego` 为 owner |

项目的 `database/` 目录只保存代码和文档。

## 批量入库

先填写数据库连接配置，并完成建表；已有四字段 L1 表需先执行上述迁移。
然后在项目根目录运行入库脚本：

```bash
python -m roboego_hand_vis.database.ingest --table l1data \
  ks3://baai-eai-datasets/data/cp_0002_session_20260923_112929 \
  ks3://baai-eai-datasets/data/cp_0002_session_20260923_103724 \
  ks3://baai-eai-datasets/data/cp_0002_session_20260923_103758
```

脚本输出 JSON，包含每条数据的 ID、KS3 路径、入库结果和下载状态。
`result: created` 表示新入库，`result: existing` 表示该路径已经入库；
`created_count` 和 `existing_count` 是本次新增和已有记录的数量。
新记录的下载状态和 L1 各阶段状态均为 `pending`，`local_path` 为 NULL。
重复执行返回已有记录，不覆盖本地路径、下载状态或阶段状态。
并发入库依靠表内 KS3 路径唯一约束，只有一个调用能创建同一条记录。

路径较多时，可放入 UTF-8 文本文件 `ks3_paths.txt`，一行一个完整 KS3 路径：

```bash
python -m roboego_hand_vis.database.ingest --table l1data --file ks3_paths.txt
```

空行和以 `#` 开头的注释行会被忽略；也可同时传入命令行路径和文本文件。
脚本先校验全部输入路径，再逐条提交入库。如果数据库中途报错，已提交记录会保留，
修复连接后重新执行即可继续。此脚本不检查 KS3 远端对象是否存在，也不下载文件。

入库后，下载程序通过 `DataService.claim("l1data")` 领取下一条 `pending` 记录，
使用返回的 `ks3_path` 下载到共享目录，再调用 `complete()` 或 `fail()` 回写结果。
`claim()` 成功后状态变为 `processing`，其他进程不会领取同一条记录。

已经提供独立的 [L1 下载入口](../download_data/README.md)。从数据库下载前三条：

```bash
python -m roboego_hand_vis.download_data.l1 --database --output-dir ./data/l1 --limit 3
```

## Python 使用

```python
import os
from pathlib import Path
from roboego_hand_vis.database import DataService, get_database_url

db = DataService.from_url(get_database_url())
shared_root = Path('/mnt/shared/roboego')  # 各服务指向同一共享存储

try:
    row = db.register('L1data', 'ks3://my-bucket/raw/session001.mp4')
    # 重复登记返回原记录，不重置下载状态或本地路径。
    row = db.get('L1data', row['id'])
    if row['download_status'] == 'completed':
        path = shared_root / row['local_path']
        if not path.exists():
            raise FileNotFoundError(f'共享文件缺失，需要核查：{path}')
        print('直接使用：', path)
    elif row['download_status'] == 'pending':
        task = db.claim('L1data', row['id'])
        if task is not None:
            # 只有领取成功的进程可以下载并回写该任务。
            # 调用自己的 KS3 下载逻辑：先写唯一临时路径，校验后在同一
            # 文件系统内原子重命名到 shared_root / relative_path。
            # 文件发布成功后：
            # db.complete('L1data', task['id'], relative_path)
            # 下载失败、停止写文件后：
            # db.fail('L1data', task['id'])
            print('已领取，请交给下载器：', task)
    else:
        print('等待进行中的下载，或检查失败原因：', row['download_status'])
finally:
    db.engine.dispose()
```

上述示例中的 KS3 下载需要接入自己的下载器；单独运行示例会领取并保留
`processing` 状态。`complete()` 不检查文件是否存在，调用方须先完成校验和发布。
`local_path` 使用 `/` 分隔的相对路径，例如 `L1/session001/video.mp4`；
不接受绝对路径、Windows 盘符、反斜杠或 `..`。应避免使用指向共享根目录外的符号链接。
不同表的数据使用不同的子目录，避免文件名冲突。

接口说明：

| 方法 | 行为 |
| --- | --- |
| `register(table, ks3_path)` | 并发安全地登记或返回已有记录 |
| `register_if_absent(table, ks3_path)` | 返回 `(记录, 是否新增)`，用于区分入库结果 |
| `get(table, id)` | 返回记录，不存在时返回 `None` |
| `claim(table, id=None)` | 原子领取指定 pending 记录；省略 ID 时领取下一条可用记录 |
| `complete(table, id, local_path)` | `processing → completed`，写入路径 |
| `fail(table, id)` | `processing → failed`，清空路径 |
| `retry(table, id)` | `failed → pending`，下一次领取后再下载 |

三个状态更新方法返回布尔值；`False` 表示记录不存在或状态不符合要求，
调用方应重新查询，而不是认为更新成功。失败记录不会无限自动重试。

## 并发和恢复边界

`claim` 使用短事务内的 `FOR UPDATE SKIP LOCKED` 和更新语句，提交后返回。
多个进程同时领取同一条记录时只有一个成功，其他返回 `None`；
`None` 也可能意味着该记录正被其他事务锁定，可以稍后重查。
每个进程分别创建 `DataService`，不要跨进程共享连接池；同一进程内可以在线程间共用。
下载文件期间不持有数据库事务或连接。

只保留四个字段意味着没有 worker 标识、租约或心跳，因此不自动重领
`processing` 记录，也无法在数据库层验证回写者的身份。
只有成功领取的下载器才应调用 `complete` 或 `fail`。

如果下载进程崩溃，必须先确认原进程已经停止、不会继续写文件或更新数据库，
再人工将对应记录重置。以下 SQL 在 PostgreSQL 客户端中执行，替换表名和 ID：

```sql
UPDATE l1data
SET download_status = 'pending', local_path = NULL
WHERE id = 123 AND download_status = 'processing';
```

若 completed 的共享文件丢失，应先确认共享存储已正确挂载；确实丢失时可在协调
相关服务后使用相同方式重置，WHERE 条件改为 `download_status = 'completed'`。
不要仅因等待时间较长就重置正在运行的任务，否则可能出现重复下载和旧进程回写。

使用可丢弃的 PostgreSQL 测试库。测试用户需有创建 schema 的权限；
测试创建随机名称的 schema，结束后删除，不使用业务表。

```bash
export TEST_DATABASE_URL='postgresql+psycopg://USER:PASSWORD@127.0.0.1:5432/TEST_DB'
python -m pytest tests/database -q
```

覆盖模型与 YAML 字段一致性、阶段状态约束、迁移保留数据与重复执行、独立自增 ID、
并发去重、任务争抢、跳过锁定记录、事务回滚和路径校验。
未设置 `TEST_DATABASE_URL` 时跳过数据库测试。
